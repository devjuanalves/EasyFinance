# Block 9A API contracts

Contract inventory prepared before route implementation. Prefix `/api/v1`. JSON response `{data: ...}`; error `{error: {code, message}, requestId}`. UUID IDs, ISO dates, integer minor units as decimal strings. Unknown body/query fields are rejected. No caller-supplied actor, workspace ownership or source metadata. Workspace IDs come from the authorized path, never writable entity bodies.

All mutations require exact configured Origin plus `X-EasyFinance-CSRF: 1` and JSON. Cookie SameSite=Strict; production Secure, no Domain, Path=/api/v1. GETs never mutate domain state. CORS grants only configured origin, credentials enabled. Public auth rate limiting is per IP plus normalized-email hash; process-local bounded state. Session errors 401; missing/inaccessible workspace/resource 404; forbidden role 403; validation 400; stale/conflicting writes 409; rate 429; unavailable DB/recovery 503. Authentication failure responses do not reveal account existence. Registration deliberately does not authenticate: UI proceeds to login after the same neutral response for new/existing email.

Not implemented here: accounts management after the onboarding account, imports, split replacement, transfer creation/correction, invoice/payment writes, investments, invitations/acceptance, automations, assistant persistence or notifications. Existing records retain their source/splits/transfer semantics; unsupported mutations are blocked rather than silently discarding relationships.

A payment key is workspace-wide and immutable: identical retries return the original payment; changed payload/invoice/actor conflicts. Account balances derive from opening balance plus non-excluded signed transactions; transfers affect individual balances but remain neutral in income/expense totals.

## Block 9B.3 investment contracts

All routes are under `/api/v1/workspaces/:wid`; authenticated active membership is mandatory. Owner/Editor may mutate, Viewer may read. No browser role claim is accepted. Existing CSRF and error envelopes apply.

| Operation          | Method / route             | Request                                                                      | Response / transaction                                                                                                                                          |
| ------------------ | -------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Portfolio records  | GET /investments           | No query                                                                     | Scoped accounts, holdings, dated movements, valuations, audit history, positions and currency-separated summaries; bounded complete history for accurate replay |
| Investment command | POST /investments/commands | UUID key, action, payload, expected investment version for existing holdings | Result ID and updated scoped records; one transaction including audit and idempotency                                                                           |

Commands are an explicit allowlist matching existing UI actions: createAccount, create, update, recordMovement, editMovement, deleteMovement, valuation, deleteValuation. Payload fields are validated separately per action; IDs/workspace/actor/derived money cannot be mass assigned. Metadata updates cannot change historical type/currency. Corrections and soft deletions require confirmation and replay all later history. Creates and movements calculate amounts on the server from exact decimal inputs; response monetary values are safe bounded integer cents. Quantities/prices are decimal strings. No cash ledger write occurs.

Each command key is scoped to workspace and actor with a normalized request fingerprint. Identical retry returns the original result; altered retry conflicts. Existing-holding mutations require its current version. User/workspace locks serialize authorization and financial replay across independent API connections. Responses use 400 validation, 401 session, 403 role, 404 inaccessible resource, 409 stale version/idempotency conflict, and existing safe database errors. History is limited to 10,000 rows per entity; exceeding this fails explicitly rather than returning a partial financial calculation.

## Block 9B.5 — received-income client attribution

`GET /workspaces/:wid/income/summary` retains its existing contract. With `clientId`, confirmed receipt allocations are attributed to the invoice client; only a directly client-tagged transaction's unallocated remainder is attributed directly. An untagged remainder belongs only to the unfiltered cash total. This supports one receipt allocated across clients without duplicating income. Account/currency/booking-date filters still scope cash; invoice issue dates scope billed/outstanding metrics. No migration or new endpoint is required.
