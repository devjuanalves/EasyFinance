## Authentication review

Preserved Argon2id with random 128-bit salts, 19,456 KiB memory, two passes, parallelism one and 32-byte hashes. Password validation is 12–128 characters; hashing concurrency is bounded to four operations. A dummy hash path handles absent users; comparisons use `timingSafeEqual`. Registration/login use generic account responses. Exact timing equality is not claimed.

Sessions contain 256 random bits; PostgreSQL stores SHA-256 hashes only. HttpOnly, SameSite=Strict cookies are scoped to `/api/v1`, have no Domain, and require Secure in production configuration. Sessions expire after 12 hours or seven days for remember-me; there is no sliding renewal. Password changes revoke all sessions atomically under the user lock. Logout revokes the current session. Every protected service rechecks session validity and active server-side workspace membership; client mock identity or role claims cannot authorize persisted records. Owner/Editor/Viewer and cross-workspace/revocation regressions remain in the live suites.

Mutations require the exact configured Origin, JSON and `X-EasyFinance-CSRF: 1`; CORS grants only the configured origin. Reverse-proxy trust is now explicitly false. Forwarded IP headers cannot select limiter identities. Auth endpoints have process-local IP and normalized-email throttles, bounded maps and expiry; the hashing concurrency bound adds load protection. These are not distributed controls. Any future proxy deployment must review trusted proxy addresses/hops, effective client IPs, TLS termination and shared throttling together; never enable blanket proxy trust.

## Recovery and email verification: deliberately unavailable

The existing `PasswordResetToken` supports an account foreign key, unique token hash, expiry and used timestamp. `User.emailVerifiedAt` exists, but there is no purpose-separated verification token model. `ActivityLog` requires a workspace, so it cannot truthfully audit a not-yet-onboarded account reset as an account-wide durable event without a reviewed design.

No verified delivery provider, account-wide durable recovery audit contract or verification flow exists. Consequently this block **does not implement issuance/consumption/reset endpoints or a test transport**. Adding an unreachable token issuer or returning tokens to compensate for missing delivery would provide no safe user workflow. The existing rate-limited `POST /api/v1/auth/recovery` retains the same 503 `RECOVERY_UNAVAILABLE` for existing and unknown addresses, sends no message and writes no token. Live tests verify that boundary. The runtime role has no reset-token grants. No reset-token concurrency or verification lifecycle is claimed tested, because neither lifecycle is implemented. Existing onboarding identities remain valid and unverified; email-address possession is not established by registration. Invitation acceptance therefore remains unsuitable as production mailbox-ownership proof.

Required future lifecycle: use 32 random bytes, store only a hash, bind the account and purpose, configurable short expiry (proposed 15 minutes), neutral issuance response and independent request/consume throttles. Lock the user before rechecking/consuming the token in one transaction; atomically replace the password, invalidate all outstanding reset tokens and sessions and persist a minimal account-level audit record. Concurrent consumers must produce exactly one successful reset. Deliver only through an authorized provider using a fixed allowlisted HTTPS origin, never request Host headers. Do not put tokens in logs, API listings or browser storage. Consume via POST, prevent referrer leakage, and do not automatically sign in. Verify expiry, replay, cross-account misuse, failure rollback and independent-connection races before enabling delivery. Verification needs its own purpose-separated lifecycle; do not reuse reset tokens or mark an email verified merely because a password changed.

## Configuration, privileges and reliability

`API_MODE=api`, `VITE_AUTH_MODE=api`, an explicit `WEB_ORIGIN`, server-only `API_DATABASE_URL` and the disposable acknowledgement select local persistence. `DATABASE_URL` is the separate administration/migration identity. No VITE variable may contain credentials. Default local mode is a demonstration; production configuration rejects demo mode and non-HTTPS origins. Explicit mock builds remain labeled previews and never authenticate API requests. The existing database safety guard still rejects production runtime entirely: this is not a deployment configuration.

Runtime startup now rejects missing/short passwords and common placeholder prefixes before opening a connection. Use generated credentials, not a 16-character predictable password; the validation is a configuration mistake check, not entropy measurement. No credentials are stored in source, logs or public responses. Root environment files and temporary evidence remain ignored. Secret rotation, managed secret storage and production identity provisioning remain operator responsibilities.

The single PrismaPg pool has at most ten connections, a two-second connection acquisition timeout, 30-second idle pool timeout and ten-second PostgreSQL statement timeout. Existing role-level idle-in-transaction timeout is 15 seconds; service transaction limits remain in place. Startup diagnostics now also reject replication-capable roles. Tests verify that the restricted role cannot create schema objects, delete users, truncate any domain table or access reset tokens; DELETE remains limited to invoice_items for draft replacement. It has no superuser, CREATE DATABASE, CREATE ROLE, replication, bypass-RLS, schema CREATE or object ownership. Grants were not expanded. Table permissions are not RLS: authorization remains application-enforced and credentials still require protection.

HTTP request/header/inactivity bounds are 30/15/30 seconds. SIGINT/SIGTERM marks readiness false, stops accepting requests, drains HTTP and disconnects Prisma, with a ten-second process deadline. In-flight writes still need their normal transaction/error handling; a network timeout is not a guarantee that a command did not commit. Clients must use existing idempotency keys and review state before retrying.

`GET /api/health` keeps its exact database-independent liveness contract. New `GET /api/ready` returns only `{status: 'ready'}` with 200 or `{status: 'not_ready'}` with 503. It executes a database probe, coalesces simultaneous probes, bounds the response to three seconds and reports false without persistence, during shutdown or on database failure. Underlying statements are bounded separately; the response deadline does not cancel SQL. No database identity/version/credentials are exposed. Tests cover absence, failure/recovery, coalescing, deadline and shutdown; live lifecycle checks include readiness and clean SIGTERM.

## Operational logs and incident response

Request IDs are generated by the server. Authentication outcomes log only a fixed event/action, status and request ID on response completion, including rejected attempts and Express case/trailing-slash path variants. Startup/shutdown/listener/startup failures use structured fixed events; normal startup no longer prints database identity. Existing 500/503 error logs contain only a safe code and correlation ID. No raw request/error objects, cookies, passwords, token values, email addresses, financial descriptions or connection URLs are serialized. Tests enforce the allowlist. These stdout records are operational observations, not durable transactional audit records or proof of delivery.

Before deployment, designate an on-call incident lead and database recovery owner, ship these logs through access-controlled encrypted storage, define retention and alerts (readiness failures, 5xx/429 spikes, authentication abuse, backup freshness, restore failures), and test escalation. Avoid logging request bodies or authorization headers at the reverse proxy. For suspected credential compromise: contain access, rotate affected credentials, revoke relevant sessions, preserve restricted evidence, assess tenant scope and notification obligations, then restore service under an approved incident plan. No monitoring vendor, alert scheduler or production incident service was configured here.

## Fictional backup/restore rehearsal and runbook

`scripts/operations/backup-rehearsal.js` requires `EASYFINANCE_BACKUP_REHEARSAL=yes`, the existing disposable acknowledgement, non-production mode and the exact loopback CI control target. It creates randomly named **new source and restore databases** on the isolated test cluster, fails on name collisions, applies the unchanged migration and seeds only the fresh source. It never dumps the configured developer database. The source is verified to have exactly one fictional `@example.test` user and no password hash before dump creation.

The native PostgreSQL 18 custom-format dump excludes ownership/ACLs. The distinct new restore uses `--exit-on-error --single-transaction`, never `--clean`, reset or drop. Verification compares all table row counts and content hashes, constraint definitions and deferred trigger definitions, then runs the financial integrity suite against the restored database. Dump/verification artifacts stay in an ignored directory with mode 0700 and files 0600. Credentials are passed through the local subprocess environment, not command-line URLs or output. This is appropriate only for the acknowledged local rehearsal; production needs a managed credential mechanism. No dump is eligible for GitHub artifact upload.

Local command after provisioning the isolated CI target and exporting its ignored environment:

```sh
EASYFINANCE_BACKUP_REHEARSAL=yes PG_BIN=/Library/PostgreSQL/18/bin node scripts/operations/backup-rehearsal.js
```

Omit PG_BIN when matching PostgreSQL-native tools are already on PATH. The script leaves its fresh databases for inspection; stopping the owned temporary cluster is separate from deleting data. Never point it at a shared/developer database or remove its guards.

Production procedure remains a proposal: backup the reviewed database/schema/data/migration metadata with a supported `pg_dump --format=custom`; export role/grant provisioning separately without password hashes. Use a dedicated read/backup identity with reviewed visibility and no application DDL authority. Encrypt before leaving the secured host, use encrypted transport and separate-key access-controlled storage, validate checksums and archive listings, and regularly restore into an isolated empty target. Apply reviewed runtime grants separately, verify migration compatibility, constraints, row/data reconciliations and functional financial tests before any cutover. Record duration, backup age, verification outcome and accountable operator. Native logical dumps are not PITR; assess WAL archiving/base backups if the approved RPO needs it.

Candidate policy requiring owner approval: daily backups, 30 daily and 12 monthly retention points, RPO at most 24 hours and RTO at most four hours; test rather than promise those targets. Include legal retention/deletion obligations, immutable copies, key recovery and restore drills. Only fictional unencrypted local rehearsal files were created; **no production backup, encryption system, schedule, retention enforcement, RPO or RTO has been established**.
