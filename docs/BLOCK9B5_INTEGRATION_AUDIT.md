# Block 9B.5 — system integration audit

Reviewed 25 November 2026, Australia/Sydney, on `feat/backend-9b5`. Scope: existing V1 integration, financial correctness, authorization, regression and preservation. No new module, aggregation service, migration, seed reset or deployment was introduced.

## Executive assessment

The implemented persistent domains share authenticated workspace boundaries and reconcile cash through the transaction ledger. Investments intentionally maintain a separate portfolio book. Home, Dashboard and Categories/Rules remain demonstrations even in API mode. Passing the local tests below establishes the tested development behavior, not production readiness.

One High financial-reporting defect was reproduced and corrected: filtering received income by client omitted allocations of pre-existing bank receipts with no transaction client tag. The fix attributes confirmed allocations to the invoice client and attributes only the unallocated remainder to a directly tagged client. The overall cash total remains unchanged. No financial records were rewritten.

## Home and Dashboard provenance

`WorkspaceProvider.jsx` creates the browser financial store from `financialData` plus demo settings; scenario loading uses `getFinancialData` and the `financial-demo` query key. It does not fetch PostgreSQL financial records. Home's assistant service uses deterministic intent/fixture calculations, initial conversations and session history. Attachment selection does not process files. Suggestion navigation may open real domain routes, but its displayed amounts remain fixture-derived.

`DashboardPage.jsx` calls `summarize` from `data/calculations.js` on that store. Income, expense, net cash flow and savings rate come from included demo ledger rows; prior-period comparison uses the equally sized preceding date window. Cash-flow chart buckets and category distribution use those same rows. Account balance combines demo opening balances and ledger activity. Unpaid invoice amounts/counts come from demo invoices. Review counts (uncategorized, duplicate and reconciliation) use demo flags. Investment cards use the demo portfolio selectors and fixture valuations. Explanatory insights are deterministic text, not AI output. Labels, headings and welcome copy are static presentation content; no live market/bank data feeds exist.

Read-only integration requires agreed reporting dates, account/workspace/currency scope, aggregation/pagination contracts, reconciliation semantics and a shared authenticated query context. Existing expense/income summary and investment snapshot APIs can supply some values but do not constitute an approved complete Dashboard aggregation contract. Do not stitch currencies together or imply demo Home changes after a persistent payment. Priority: first define cash/balance/invoice aggregate contracts, then connect chart/review endpoints, then separately authorize assistant persistence and AI boundaries. No aggregate service was added here.

## Cross-module financial results and corrected defect

The new `system-journey.spec.js` uses one real browser session/workspace. Registration and financial setup use authenticated API calls; login/onboarding, duplicate review, valuation, profile and automation configuration use UI controls. Existing domain suites separately exercise full invoice, transaction and investment editors. This is a connected hybrid API/UI journey, not a claim that every command was entered through the UI.

The journey creates an AUD 12.34 expense, categorizes it, issues an AUD 100 invoice, records AUD 40 then AUD 60 receipts, and verifies outstanding 60 then zero and cash balance AUD 87.66. A CSV candidate for the first receipt is explicitly excluded during review; the account remains unchanged. Fractional portfolio purchase/sale and a saved valuation also leave cash unchanged. Refresh preserves invoice, valuation and automation state. Viewer write rejection, revocation and final logout deny protected reads. Existing import integration coverage also exercises explicit matching to existing receipts/paired transfers, rather than only exclusion.

The High client attribution defect was reproduced as actual `receivedMinor = 0` versus expected `4000`. The regression allocates one AUD 100 bank receipt across two different clients (40 and 50), leaving 10 unallocated. Their filtered totals are 40 and 50, overall cash stays 100, and payment-date/currency filtering remains correct. The implementation does not alter transaction client ownership or create another receipt. Confirmed allocations take precedence for their portions; a directly tagged client's remainder is retained. An untagged remainder is unassigned and therefore appears only in the unfiltered total. Invoice issue-date filtering still controls billed/outstanding metrics; booking-date filtering controls received cash.

Cash totals use BigInt minor units and decimal-string JSON serialization. Invoice quantity/price/tax calculations reuse shared deterministic rounding: fractional items, proportional discount and tax reconcile to SQL checks. Invoice creation/issuance never creates cash. Payment creation/allocation/audit is atomic; existing receipt allocation consumes remaining funds only. Cancelled/draft invoices cannot accept payments and issued invoices are locked against destructive editing. Transfers affect individual balances but are neutral to income/expense; excluded transactions are omitted from financial totals. CSV decimal-comma/grouping/debit-credit normalization is tested. Investment quantities/prices retain eight decimal places; weighted-average partial-sale basis, fees, realized result, corrections and valuation invalidation are independently tested. Sale proceeds are not wholly profit and unrealized values do not create cash. Currency aggregation never silently converts.

## Security, concurrency and reliability

Passwords use salted Argon2id (19,456 KiB, two passes, parallelism one) with bounded concurrent derivations. Login failures are generic; sessions are random opaque tokens with only SHA-256 hashes persisted, expiring after 12 hours or seven days with remember-me. Cookies are HttpOnly, SameSite Strict, scoped to `/api/v1`, and Secure in production. Mutations require exact configured Origin, JSON and the custom CSRF header. Auth attempts are limited by IP and normalized-email hash; rate state is bounded but process-local. Tokens are not stored in browser storage. Unknown/mass-assigned fields are rejected, including roles, ownership and computed financial totals.

Every protected service rechecks session/user and database membership; frontend mock identity cannot satisfy that check. Cross-workspace IDs, filters and guessed records are tested. Pending invitations grant no membership. Revocation is now tested across ten domain read endpoints and a financial mutation after previously successful reads. Invite tokens are hashed, expiring and recipient-bound; local handoff is explicit and no delivery is claimed. Runtime `easyfinance_9a_app` is not superuser, database/role creator, RLS bypasser, schema creator or table owner. Applied grants are inspected; automation run writes are absent. Application scoping remains essential because there is no row-level security.

User/workspace locks order permission changes and financial commands; optimistic versions reject stale edits. Independent-client races cover payments, repeated import confirmation, transaction updates, investment commands, invitation acceptance and automation edits. Unique operation identities and atomic audit writes prevent duplicate supported commands; rollback tests force failure after intermediate writes. This is tested serialization within those service paths, not a claim of universal serializable isolation. Profile/workspace metadata writes do not expose a general optimistic version contract; simultaneous authorized metadata writes may be last-writer-wins. Financial transaction locks must not be removed as a performance shortcut.

Central errors hide SQL/credentials and provide request identifiers. Database-unavailable mapping to safe 503 is unit-tested with injected failures; PostgreSQL was not stopped during this audit. Health is process liveness, not a DB readiness probe. The runtime creates one pooled Prisma client (maximum ten connections/process), disconnects during graceful shutdown and uses a ten-second service transaction timeout. Production needs explicit pool sizing, monitoring, migration/recovery procedures and readiness checks.

## Performance observations

Ten sequential authenticated reads against small fictional local fixtures took 12–72 ms (22, 55, 45, 20, 40, 72, 12, 27, 22, 21). This bounded smoke measurement ran alongside other checks and is not a benchmark/SLA or load test.

Account balance listing performs one aggregate per account (N+1). Expense/income summaries scan matching rows; invoice status filtering/pagination currently materializes matching invoices before slicing. Clients and invoice detail history are not comprehensively paginated. Client attribution additionally reads confirmed allocations. These are Medium scaling risks requiring measured SQL aggregation/pagination work before larger deployments. Investment snapshots bound each history collection at 10,000 records but still replay history and scan audit data. CSV input is bounded to 500 rows with a 6 MB JSON limit, and duplicate review refuses accounts over its 10,000-record review boundary; candidate comparisons still grow with rows × existing records. Import history shows 50 batches. Settings member/config collections cap at 500 and invitation/run/audit collections at 100, without complete pagination. Workspace locks serialize reads as well as writes, limiting throughput. No destructive or high-volume load test was run.
